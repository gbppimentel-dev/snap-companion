# how it works

The Android service layer reads supported saved-data containers and transient screen observations. A bundled HTML/CSS/JavaScript interface displays those facts and offline references. It has no remote backend or Internet permission.

## saved data

The fixed-purpose AYN bridge verifies the targeted Eden Duo package and Snap title identity, then reads bounded metadata/image records. Stable revisions, file dimensions, encrypted envelopes, CRC32/Adler32 checksums, source/profile bindings and supported IDs gate adoption. Unknown records are not assigned invented meanings.

Photodex metadata, request registries and research revisions refresh independently. Images are copied one record at a time in supported quiet scenes, with a quiet-state recheck before import. Current official photo slots enter the UI; prior private records remain stored separately.

## observations

The capture service reads a bounded upper-display image using Android MediaProjection and bundled offline Latin OCR. Accepted bitmaps remain owned until a terminal success/failure releases them. Result publication occurs on the capture worker and requires the current source/generation and a fresh capture timestamp. Resizing, recognition pause, connection changes and shutdown invalidate older work.

The supported direct reader supplies current course/variant and selected level after exact-build and object-ownership validation. Supported screen labels remain available for screen-only observations; they do not override a fresh verified game context. Saved research progress, manual historical records and reference filters cannot become current selected-run context. Photo Selection keeps the normal dashboard; neither a comparison desk nor a grading helper is shown. Recognition/save safeguards remain active.

## workload and lifecycle

One OCR request is in flight. Duplicate suppression, adaptive cost/thermal budgets and bounded failure backoff limit work. The passive native controller reader observes supported built-in input without grabbing or injecting events; the display updates from state and expiry timers. Hiding the companion clears stale highlights and stops its clock updates.

The existing AYN priority helper can adjust scheduling groups for visible Eden and performs a guarded startup focus/pause repair. These are fixed firmware operations, not saved-game edits or ordinary game-input injection. Their firmware dependence is part of the compatibility boundary.

The UI permits only bundled assets and private current-photo responses. It blocks arbitrary file/content/network navigation. Original saves are not written. Private diagnostic metrics contain opaque sessions/epochs and counters rather than OCR text, profile IDs or photographs.

## live route and view

A Thor-specific read-only native helper validates the owned game fingerprint and active object ownership before supplying course, selected level, rail geometry/distance, pose and render-camera orientation/lens readings at20Hz. Java and the map model whitelist and validate the game fields; session/process metadata never enters the WebView feed. The camera follows an owned world/primary-camera chain, verifies type/update identity and consistent pose reads, then revalidates ownership. Its normalized forward/up vectors, vertical FOV and aspect produce a guarded schematic cone.

The illustrated map matches directed rail geometry against the factual catalog. Branch prefixes, mandatory continuations and observed transitions drive section/current-path progress; uncertain histories retain ranges or stay unknown. Bounded calibration intervals map measured rail distance to the illustration. Shared measured junctions receive small local alignment corrections; rejected gaps are never interpolated. Map-coordinate marker groups are deterministic under panning, and pins remain fixed-size in a separate unscaled portrait overlay through zoom. Photography-tool buttons are absent from the map; the original passive controller feedback remains.

The APK resolves a typed scene back to its current controller: standard courses and Research Camp have different controller types and scene-owner fields. Both scenes share the verified render context, so Camp uses the same typed-camera checks as other courses. Camp's photo count comes from its current world's shared-owned HUD vector and exact current rail, with repeated ownership/vector/counter checks. Only the bounded integer reaches the dashboard; no guest pointer is exported. Standard courses use a bounded lookup of the game’s named HUD registration, then prove that HUD’s weak world reference is alive and that the same world owns the exact HUD/control pair. Registry identity, alias type, world/HUD shared headers, rail, phase, vector bounds and counter are checked again to reject replacement during a read. Missing or changing ownership withholds only the native count; the original screen-reading fallback remains. The path has been checked in Park Day, not every course.

The dashboard activity uses Android’s single-task launch policy. Reopening its launcher or an explicit app intent reuses the existing activity instead of stacking another WebView, controller subscriber and memory-reader owner. The normal Android Back gesture still dismisses in-app overlays and can leave the dashboard from Live.

## Event continuity and device charge

A scoped owned expedition can yield a fresh rail reading during an event phase.
The map can use that measured rail/distance without enabling gameplay tools,
photo counters or camera cones in the event. A failed consistency reread is
seeking, not evidence of an ended expedition; ownership checks are retained.
Branch history tolerates gaps up to five seconds. A missing/unmapped reading can
retain an explicitly labelled stationary marker for at most 2.5 seconds. Known
exits, source/run/course changes and visibility loss clear it. No motion is
extrapolated. Unaligned intervals remain unmapped.

Android's sticky battery broadcast supplies current charge and charging state,
read at most once per 15 seconds. Only the icon/charge percentage is displayed;
there is no health/Good label or capacity estimate.

and native ownership guards. There is no stock/Duo auto-detection. A visible
