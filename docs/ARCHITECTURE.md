# how it works

The Android service layer reads supported saved-data containers and transient screen observations. A bundled HTML/CSS/JavaScript interface displays those facts and offline references. It has no remote backend or Internet permission.

## saved data

The fixed-purpose AYN bridge verifies the original Eden package and Snap title identity, then reads bounded metadata/image records. Stable revisions, file dimensions, encrypted envelopes, CRC32/Adler32 checksums, source/profile bindings and supported IDs gate adoption. Unknown records are not assigned invented meanings.

Photodex metadata, request registries and research revisions refresh independently. Images are copied one record at a time in supported quiet scenes, with a quiet-state recheck before import. Current official photo slots enter the UI; prior private records remain stored separately.

## observations

The capture service reads a bounded upper-display image using Android MediaProjection and bundled offline Latin OCR. Accepted bitmaps remain owned until a terminal success/failure releases them. Result publication occurs on the capture worker and requires the current source/generation and a fresh capture timestamp. Resizing, recognition pause, connection changes and shutdown invalidate older work.

The supported direct reader supplies current course/variant and selected level after exact-build and object-ownership validation. Supported screen labels remain available for screen-only observations; they do not override a fresh verified game context. Saved research progress, manual historical records and reference filters cannot become current selected-run context. Photo Selection uses current recognized subject/category fields plus saved benchmarks; Grading has no dedicated helper.

## workload and lifecycle

One OCR request is in flight. Duplicate suppression, adaptive cost/thermal budgets and bounded failure backoff limit work. The passive native controller reader observes supported built-in input without grabbing or injecting events; the display updates from state and expiry timers. Hiding the companion clears stale highlights and stops its clock updates.

The existing AYN priority helper can adjust scheduling groups for visible Eden and performs a guarded startup focus/pause repair. These are fixed firmware operations, not saved-game edits or ordinary game-input injection. Their firmware dependence is part of the compatibility boundary.

The UI permits only bundled assets and private current-photo responses. It blocks arbitrary file/content/network navigation. Original saves are not written. Private diagnostic metrics contain opaque sessions/epochs and counters rather than OCR text, profile IDs or photographs.

## live route and view

A Thor-specific read-only native helper validates the owned game fingerprint and active object ownership before supplying course, selected level, rail geometry/distance, pose and render-camera orientation/lens readings at20Hz. Java and the map model whitelist and validate the game fields; session/process metadata never enters the WebView feed. The camera follows an owned world/primary-camera chain, verifies type/update identity and consistent pose reads, then revalidates ownership. Its normalized forward/up vectors, vertical FOV and aspect produce a guarded schematic cone.

The illustrated map matches directed rail geometry against the factual catalog. Branch prefixes, mandatory continuations and observed transitions drive section/current-path progress; uncertain histories retain ranges or stay unknown. Bounded calibration intervals map measured rail distance to the illustration. Shared measured junctions receive small local alignment corrections; rejected gaps are never interpolated. Map-coordinate marker groups are deterministic under panning, and pins remain fixed-size in a separate unscaled portrait overlay through zoom. Photography-tool buttons are absent from the map; the original passive controller feedback remains.

The APK resolves a typed scene back to its current controller: standard courses and Research Camp have different controller types and scene-owner fields. Both scenes share the verified render context, so Camp uses the same typed-camera checks as other courses. Camp's photo count comes from its current world's shared-owned HUD vector and exact current rail, with repeated ownership/vector/counter checks. Only the bounded integer reaches the dashboard; no guest pointer is exported. Standard-course photo counts retain the screen-reading provider until equivalent world ownership is qualified.
